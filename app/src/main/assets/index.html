WWE WII PAC EDITOR BY JATIN(MOD PLACE WII)

Reads the table of contents out of PAC, PACH, DPK8, EPK8, EPAC and HSPC archives, lets you browse into nested containers without extracting first, and extract or inject individual entries — entirely in your browser. Nothing is uploaded anywhere.

Format coverage: PAC / PACH / DPK8 / EPK8 / EPAC / HSPC headers are parsed directly. SHDC and DPAC containers still aren't handled.
EPAC: packs a recursive directory tree (mixing files and sub-directories at any depth) into a fixed 16KB header table — the same 2048-byte first row and 16KB size as DPK8/EPK8. Entries are shown flattened with their full path (e.g. SSFA\0100); a nested entry whose own data happens to be another recognized archive (PAC/PACH/DPK8/EPK8) still gets an Open button. Renaming and Injecting (including growing) work the same as other formats; + Add file isn't supported for EPAC.
HSPC: a 64-byte header, two index tables and the file data, in a fixed 16KB header area with a 2048-byte block size. Unlike the other formats it stores no text names — each entry is identified by a 64-bit name hash, shown here as 16 hex digits in the same byte order as in the file (entries with no matching hash record fall back to fileNNNNNN). File offsets are in 2048-byte blocks counted from the start of the container itself (not from the end of the header), and sizes are in 256-byte units. Rename edits the entry's 64-bit hash directly. Inject works like the other block-based formats, including growing: every later offset is rewritten, and the container's own size totals in its header (0x24, 0x2C, 0x3C) are kept in step. Two header fields whose purpose isn't known (0x10 and 0x28) are never touched, and 0x2C being treated as \"container blocks + 1\" is inferred from a single sample file. + Add file and Delete aren't supported for HSPC.
Nested containers: if an entry's own data starts with a recognized magic (PAC /PACH/DPK8/EPK8/EPAC/HSPC), an Open button appears — this browses straight into it, no extraction needed. Use the breadcrumb trail to go back up.
Nested containers under BPE: if an entry's data starts with a BPE wrapper (very common for PAC files packed inside EPAC), an Open (BPE) button appears instead. It decompresses the entry in memory and, if the result starts with a recognized magic, opens straight into it — with full Rename/Inject/Delete/+ Add file support inside, exactly as if it were a real top-level file. Nothing is written back while you're browsing; when you leave (via the breadcrumb trail) or download, any edits are transparently recompressed with BPE (reproducing the original wrapper) and written back into the original slot, growing the outer archive if needed. This works however many BPE layers deep a file is nested. If the decompressed data isn't a recognized archive, it fails cleanly with an error instead of opening garbage.
View Image (on .bpe and .dds entries) decompresses the entry in memory and shows it, with no separate Uncompress step and nothing written back to the archive. It auto-detects the format from the decompressed bytes: DDS (DXT1/DXT3/DXT5, or uncompressed 16/24/32-bit) or TGA (true-colour, colour-mapped or greyscale, raw or RLE) — the BPE entries in SSFaceHD.pac turn out to be 32-bit TGAs (half 512×512, half 256×256), not DDS. Only the top mip level of a DDS is shown. Export PNG saves what's on screen. If the data is neither, it says so and shows the first bytes.
Real ID names: PAC/PACH entries don't store text filenames, just a numeric id — "Real ID" reconstructs the hex-id name scheme the original tool used (with a [n] suffix for duplicate ids); "Generic" falls back to sequential fileNNNNNN names. DPK8/EPK8 entries already store real ASCII names and are shown as-is.
Rename: for DPK8/EPK8, edits the stored ASCII name in place (space-padded/truncated to the field's fixed width). For PAC/PACH, there's no text name to edit — only a numeric id — so "Rename" lets you set that hex id directly instead.
Uncompress runs Philip Gage's 1994 Byte Pair Encoding expansion algorithm in the browser — the same scheme implemented by the classic bpe.exe compressor tool (confirmed by disassembling it). It works on any entry (PACH included) that was BPE-compressed, and downloads the raw expanded bytes. There's no reliable way to auto-detect which entries are BPE-compressed from the bytes alone, so this is a manual, try-it-on-an-entry action — if an entry isn't actually BPE data, decompression will fail cleanly with an error rather than produce garbage.
Inject as BPE compresses your replacement file with the same algorithm before writing it into the slot. If the entry's existing data starts with a BPE wrapper header, the tool reproduces that same wrapper around the newly compressed data (one field in that wrapper has an unconfirmed meaning and is just copied from the original); otherwise it injects the raw compressed stream directly.
Inject overwrites an entry's bytes in place and updates its stored size. If the replacement is bigger than the current slot, the tool now offers to grow the archive instead of refusing: it shifts every byte after the entry (in 2048-byte-rounded steps) and rewrites every offset field throughout the archive — including inside nested containers — so everything else still resolves correctly. This is a real, in-place rebuild of the buffer; there's no undo besides reloading the original file.
+ Add file (top of the entry list) appends a brand-new entry. For a PAC/PACH container it grows the table of contents by one record and asks for the numeric id to give it. For an EPK8 container it asks which existing directory to add the file to (if there's more than one) and a filename, then inserts a new row into that directory's section of the fixed 16KB header table — a local shuffle that's safe because EPK8's offsets are anchored to the end of that table, not to their row's position within it. Both append the new file's bytes at the very end of the archive. It's not available for DPK8 — its packed fields are 16-bit rather than EPK8's 32-bit, and this tool doesn't have confirmed enough understanding of a DPK8 directory row's packed file-count field to safely add to it — nor for HSPC, whose two linked index tables and header size totals this tool doesn't yet rewrite for a new entry.
Delete removes an entry entirely: its table record and its data, shifting everything after it and rewriting offset/size fields throughout the archive — including inside nested containers — the same generic engine used for growing an injected entry, run in reverse. For PAC/PACH this is exact byte-for-byte. For EPK8 the data span removed is rounded up to a 2048-byte block, matching the convention this tool uses everywhere else for EPK8's block-quantized offsets. It's not available for DPK8, EPAC or HSPC, for the same reasons + Add file isn't. Always confirmed before it runs, and — like everything else here — there's no undo besides reloading the original file.
Once you've injected, renamed, deleted, or added anything, a Download modified archive button appears at the top level.
Extensions are still a best-effort guess from magic bytes, and byte order can be flipped above if entry counts or sizes look wrong.
TPL Preview appears on any entry tagged .tpl (GameCube/Wii CI8 texture, magic 0x0020AF30) or .bpe (since these archives commonly store TPLs BPE-compressed) — it transparently strips a BPE wrapper and decompresses first if needed, then decodes the CI8-indexed, 8×4-block-swizzled image data through its cloned palette (RGB565 or RGB5A3) and renders it to a canvas, alongside its dimensions and palette format. Not a TPL (or not BPE data) fails cleanly with an error rather than showing garbage.
Inject PNG as TPL clones that same entry's exact image/palette header bytes (so hardware flags like wrap/filter modes survive), resizes your replacement PNG/JPG to the locked dimensions, quantizes it into a ≤256-color palette matching the original's format, re-swizzles it into CI8 index data, and rebuilds a complete TPL. If the original entry was BPE-wrapped, the new TPL is recompressed and re-wrapped the same way before being written back with the normal Inject machinery (so oversized replacements still trigger the same grow-the-archive flow).
